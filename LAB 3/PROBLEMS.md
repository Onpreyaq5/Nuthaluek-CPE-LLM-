## ปัญหา 01 — ข้อมูลซ้ำและข้อมูลไม่สะอาด (Data Quality)

**ขั้นตอน:** Ingestion

### อาการ
ผลการค้นหามีเนื้อหาเดียวกันโผล่ซ้ำหลายอันดับ เอกสารอื่นที่ควรได้ที่จึงถูกเบียดตกไป
และผู้ใช้เห็นคำตอบซ้ำ ๆ ในรายการแหล่งอ้างอิง

### สาเหตุ
ฐานความรู้จริงมักถูกรวมมาจากหลายแหล่ง ทำให้มีเนื้อหาซ้ำ มีช่องว่างเกิน มีตัวพิมพ์ใหญ่เล็กปนกัน
และบางรายการขาด metadata ระบบจึงมองข้อความเดียวกันที่เขียนต่างรูปแบบเป็นคนละเอกสาร
ตัวอย่างที่ทำให้พลาดง่ายที่สุดคือข้อความเดียวกันแต่ต่างกันที่ช่องว่างท้ายบรรทัด

### วิธีตรวจสอบ
1. คำนวณลายนิ้วมือ (fingerprint) จากข้อความที่ normalize แล้ว ตัดช่องว่างออกทั้งหมด แล้วเทียบกัน
2. ตรวจว่ารายการใดขาด `cat` หรือ `level` ซึ่งจะทำให้ตัวกรอง metadata ทำงานผิด
3. ตรวจว่ารายการใดมีคำตอบสั้นผิดปกติ (< 40 ตัวอักษร) ซึ่งมักเป็นข้อมูลที่ยังไม่สมบูรณ์

### แนวทางการแก้ไข
- ทำ Normalization ก่อนเข้าดัชนีทุกครั้ง — แปลงเป็นตัวพิมพ์เล็ก ยุบช่องว่างทุกชนิดให้เหลือช่องเดียว
  และยุบอักษรที่ซ้ำเกิน 2 ตัวติดกัน
- ตัดเอกสารซ้ำด้วย fingerprint (ใช้ 160 ตัวอักษรแรกหลัง normalize)
- ไม่ทิ้งรายการที่ metadata ไม่ครบเงียบ ๆ แต่รายงานออกมาเป็นรายการให้ผู้ดูแลแก้

### ตำแหน่งใน Source Code
```
rag-normalize.js  →  normalizeText()   ทำความสะอาดข้อความ
                     fingerprint()     สร้างลายนิ้วมือเอกสาร
                     dedupe()          ตัดซ้ำ + รายงานปัญหาคุณภาพ
config.js         →  NORMALIZE_TEXT, DEDUPE_DOCS
```

### ผลการทดลอง
เดโมในหน้าเว็บจะแทรกเอกสารซ้ำและเอกสารที่ metadata ไม่ครบเข้าไปชั่วคราว 3 รายการ
เมื่อปิดการทำความสะอาด ระบบรับเข้าดัชนีทั้ง 3 รายการ เมื่อเปิด ระบบตัดรายการซ้ำออก
และรายงานรายการที่ metadata ไม่ครบแยกไว้ ฐานความรู้จริงของระบบนี้ตรวจแล้วไม่มีเอกสารซ้ำ (removed = 0)

<a name="ปัญหา-02"></a>
## ปัญหา 02 — ขนาด Chunk ไม่เหมาะสม และบริบทขาดตรงรอยต่อ

**ขั้นตอน:** Chunking

### อาการ
ค้นเจอเอกสารถูก แต่เนื้อหาที่ดึงมาถูกตัดกลางประโยค
หรือกว้างจนคำตอบจริงถูกกลบด้วยเนื้อหาหัวข้ออื่นที่อยู่ในชิ้นเดียวกัน

### สาเหตุ
- **Chunk ใหญ่เกินไป** ทำให้เวกเตอร์หนึ่งชิ้นต้องแทนหลายแนวคิดพร้อมกัน ความคล้ายจึงเจือจาง
  (เอกสารที่พูด 5 เรื่องในชิ้นเดียว จะไม่คล้ายกับคำถามเรื่องใดเรื่องหนึ่งเป็นพิเศษ)
- **Chunk เล็กเกินไป** ทำให้คำอธิบายที่ต่อเนื่องถูกหั่นขาดจากกัน เช่น สูตรอยู่ชิ้นหนึ่ง ตัวอย่างอยู่อีกชิ้น
- **ไม่มีส่วนซ้อนทับ (overlap)** ทำให้ประโยคที่คร่อมรอยต่อหายไปจากทั้งสองชิ้น

### วิธีตรวจสอบ
1. ดูสถิติความยาว chunk (ต่ำสุด / เฉลี่ย / สูงสุด) — ถ้าต่ำสุดน้อยมากแปลว่ามีเศษที่ไม่มีความหมาย
2. รันชุดทดสอบเดียวกันที่ค่าขนาดต่าง ๆ แล้วเทียบ Hit@1, Hit@3 และ MRR

### แนวทางการแก้ไข
ตัด 2 ชั้น
1. **ตัดตามโครงสร้างก่อน** — แบ่งตามบรรทัด/หัวข้อย่อย แล้วรวมบรรทัดสั้นจนใกล้ขนาดเป้าหมาย
   ทำให้แต่ละชิ้นจบความคิดในตัวเอง ไม่ขาดกลางประโยค
2. **ตัดตามขนาดเฉพาะชิ้นที่ยังยาวเกิน** พร้อมใส่ overlap 80 ตัวอักษร
3. **ใส่หัวเรื่องของเอกสารไว้ต้นทุก chunk** เพื่อให้ทุกชิ้นยังรู้ว่าตัวเองกำลังพูดเรื่องอะไร
   ไม่ใช่ข้อความลอย ๆ ที่ไม่มีบริบท

### ตำแหน่งใน Source Code
```
rag-chunk.js  →  splitByStructure()  ตัดตามบรรทัด/หัวข้อ
                 splitBySize()       ตัดตามขนาด + overlap
                 buildChunks()       ประกอบหัวเรื่อง + เนื้อหา
config.js     →  CHUNK_SIZE, CHUNK_OVERLAP, CHUNK_STRUCTURE_AWARE
```

### ผลการวัดจริง (ชุดทดสอบ 90 คำถาม)

| ขนาด | Overlap | จำนวน Chunk | ยาวเฉลี่ย | Hit@1 | Hit@3 | MRR |
|------|---------|-------------|-----------|-------|-------|-----|
| 120 | 0 | 505 | 82 | 74.4% | 90.0% | 0.817 |
| 240 | 40 | 234 | 179 | 75.6% | 91.1% | **0.832** |
| **420** | **80** | **140** | **299** | **75.6%** | **90.0%** | **0.829** |
| 800 | 100 | 77 | 544 | 74.4% | 87.8% | 0.816 |
| 2000 | 0 | 65 | 644 | 72.2% | 86.7% | 0.801 |

**อ่านผลอย่างตรงไปตรงมา:** ค่าในช่วง 120–420 ให้ผลใกล้เคียงกันมาก ต่างกันในระดับที่
**ไม่มีนัยสำคัญ** สำหรับชุดทดสอบขนาด 90 คำถาม (ต่างกัน 1 ข้อคิดเป็น 1.1%)
สิ่งที่สรุปได้อย่างมั่นใจคือ **ขนาดใหญ่เกินไปแย่ลงจริง** — ที่ 2000 ตัวอักษร MRR ลดจาก 0.829 เหลือ 0.801
ระบบเลือกใช้ 420/80 เพราะให้ผลเทียบเท่าค่าที่ดีที่สุดแต่ใช้ chunk น้อยกว่า 234 → 140 ชิ้น
ซึ่งเร็วกว่าและกินหน่วยความจำน้อยกว่า

<a name="ปัญหา-03"></a>
## ปัญหา 03 — คำที่ใช้ไม่ตรงกัน (Vocabulary Mismatch) ไทย-อังกฤษ

**ขั้นตอน:** Indexing / Query · **สถานะ: เกิดขึ้นจริงและแก้ไปแล้ว**

### อาการที่พบจริง
ผู้ใช้ถามด้วยคำไทยว่า **"ดัชนีกำลังสัมพัทธ์"** แต่เอกสาร I02 เขียนว่า **RSI**
ระบบหาไม่เจอเลย และคืนเอกสาร R08 (เรื่อง Correlation) มาเป็นอันดับหนึ่งแทน
ทั้งที่ข้อมูลที่ถูกต้องมีอยู่จริงในฐานความรู้

### สาเหตุ
1. การค้นด้วยความถี่คำต้องการให้ token ของคำถามกับของเอกสารทับกัน
   เมื่อเป็นคนละภาษาหรือคนละคำเรียก token จึงไม่ทับกันเลย คะแนนความคล้ายเป็นศูนย์
2. ปัญหารุนแรงขึ้นในภาษาไทยเพราะเขียนติดกันไม่มีช่องว่าง การตัดคำจึงคลาดเคลื่อนได้ง่าย

### วิธีตรวจสอบ
ถามด้วยคำพ้องที่ไม่เคยปรากฏตรงตัวในเอกสาร แล้วดูว่าเอกสารเป้าหมายติดอันดับหรือไม่
ถ้าไม่ติดทั้งที่เนื้อหาตรงประเด็น แปลว่าเกิด Vocabulary Mismatch

### แนวทางการแก้ไข (2 ชั้น)
1. **Character n-gram แทนการตัดคำด้วยพจนานุกรม**
   ภาษาไทยเขียนติดกัน จึงตัดเป็นชิ้นละ 2–3 ตัวอักษรแทน เช่น "แนวรับ" → แน, นว, วร, รับ, แนว, นวร, วรับ
   ทำให้จับคำย่อยได้โดยไม่ต้องใช้ตัวตัดคำภาษาไทย
2. **พจนานุกรมคำพ้องเฉพาะโดเมนการเทรด** 47 กลุ่ม เชื่อมคำไทยกับศัพท์อังกฤษแบบสองทาง
   เช่น `["rsi", "ดัชนีกำลังสัมพัทธ์", "อาร์เอสไอ", "relative strength index"]`
   เมื่อคำถามมีสมาชิกตัวใดตัวหนึ่ง ระบบจะเติมสมาชิกที่เหลือเข้าไปในคำค้น

### ตำแหน่งใน Source Code
```
rag-normalize.js  →  tokenize()         สร้าง character n-gram สำหรับภาษาไทย
rag-query.js      →  expandSynonyms()   ขยายคำพ้องสองทาง
config.js         →  TRADING_SYNONYMS   พจนานุกรม 47 กลุ่ม
                     NGRAM_MIN, NGRAM_MAX, QUERY_SYNONYM_EXPANSION
```

### ผลการทดลอง
คำถาม `"ดัชนีกำลังสัมพัทธ์ใช้ยังไง"`

| สถานะ | อันดับ 1 | ผลลัพธ์ |
|-------|---------|---------|
| ปิดการขยายคำพ้อง | R08 (Correlation) | ผิด |
| เปิดการขยายคำพ้อง (เติม `rsi`, `อาร์เอสไอ`, `relative strength index`) | **I02 (RSI)** | **ถูก** |

<a name="ปัญหา-04"></a>
## ปัญหา 04 — คำถามสั้นหรือกำกวมเกินกว่าจะค้นได้แม่น

**ขั้นตอน:** Query Understanding

### อาการ
ผู้ใช้พิมพ์แค่ `"bb คืออะไร"` หรือ `"เสี่ยง"` ระบบได้ข้อมูลน้อยเกินกว่าจะรู้ว่า
ต้องการนิยาม วิธีใช้ หรือข้อควรระวัง ผลลัพธ์จึงกระจัดกระจาย

### สาเหตุ
คำถามสั้นให้ token น้อยมาก สัญญาณที่ใช้จัดอันดับจึงบาง
ทำให้เอกสารที่บังเอิญมีชิ้นส่วนคำนั้นบ่อยชนะเอกสารที่ตอบคำถามจริง

### วิธีตรวจสอบ
เทียบผลลัพธ์ของคำถามสั้นกับคำถามเต็มประโยคที่มีความหมายเดียวกัน
ถ้าอันดับต่างกันมาก แปลว่าระบบพึ่งพาความยาวคำถามมากเกินไป

### แนวทางการแก้ไข
ทำ **Multi-Query** คือแตกคำถามเดียวเป็นหลายมุมมองก่อนค้น
- คำถามสั้น (≤ 18 ตัวอักษร) → เติม `"คืออะไร"`, `"ใช้อย่างไร วิธีใช้"`, `"ความหมายของ ..."`
- คำถามยาว → ตัดคำถามนำที่ไม่มีความหมายออก เช่น "ช่วย" "อยากรู้" "ครับ" "หน่อย"

แล้วนำทุกมุมมองไปค้นเป็นรายการแยก ก่อนรวมอันดับ (ดูปัญหา 05.1 ว่าทำไมต้องแยกรายการ)

### ตำแหน่งใน Source Code
```
rag-query.js  →  multiQuery(), transform()
config.js     →  QUERY_MULTI
```

### ผลการทดลอง
คำถาม `"bb คืออะไร"`

| สถานะ | อันดับ 1 | ผลลัพธ์ |
|-------|---------|---------|
| ปิด Multi-Query | I02 (RSI) | ผิด |
| เปิด Multi-Query | **I04 (Bollinger Bands)** | **ถูก** |

<a name="ปัญหา-05"></a>
## ปัญหา 05 — ใช้วิธีค้นเพียงวิธีเดียวแล้วแพ้คำถามบางประเภท

**ขั้นตอน:** Retrieval

### อาการ
คำถามที่มีศัพท์เฉพาะซึ่งต้องตรงตัว เช่น `61.8` หรือ `FVG` ค้นด้วยเวกเตอร์แล้วพลาด
ส่วนคำถามเชิงความหมายที่ไม่มีคำตรงกันเลย ค้นด้วย BM25 แล้วไม่เจอ

### สาเหตุ
- **BM25** ให้คะแนนจากการที่คำตรงกันตรงตัว จึงเก่งศัพท์เฉพาะ แต่ไม่เข้าใจคำพ้อง
- **การค้นด้วยเวกเตอร์** มองภาพรวมของข้อความ จึงทนต่อการใช้คำต่างกันได้
  แต่ศัพท์เฉพาะที่ปรากฏน้อยครั้งจะถูกกลบด้วยคำทั่วไป

### วิธีตรวจสอบ
รันชุดทดสอบเดียวกันด้วยโหมด `bm25`, `dense` และ `hybrid` แล้วเทียบ Hit@3 กับ MRR
ถ้าแต่ละโหมดพลาดคนละกลุ่มคำถาม แปลว่าควรรวมผลทั้งสองวิธี

### แนวทางการแก้ไข
ใช้ **Hybrid Retrieval** แล้วรวมผลด้วย **Reciprocal Rank Fusion (RRF)**

```
score(d) = Σ  w_i / (k + rank_i(d))        โดย k = 60
```

RRF รวมจาก **อันดับ** ไม่ใช่คะแนนดิบ จึงไม่ต้องปรับสเกลของสองวิธีให้เท่ากันก่อน
ซึ่งเป็นเรื่องยากเพราะ BM25 ให้คะแนนไม่มีขอบเขตบน ส่วน cosine อยู่ในช่วง 0–1

### ตำแหน่งใน Source Code
```
rag-retrieve.js  →  retrieve(), rrfFuse()
rag-index.js     →  denseSearch()  TF-IDF + Cosine
                    bm25Search()   BM25 (k1=1.5, b=0.75)
config.js        →  RETRIEVAL_MODE, RRF_K, BM25_K1, BM25_B
```

### ผลการทดลอง
คำถาม `"โปรไฟล์วอลุ่ม"` (เอกสารที่ถูกคือ A07 Volume Profile ซึ่งเขียนเป็นภาษาอังกฤษ)

| วิธีค้น | อันดับ 1 | ผลลัพธ์ |
|---------|---------|---------|
| Vector อย่างเดียว | A07 | ถูก |
| BM25 อย่างเดียว | B08 (สภาพคล่อง) | ผิด |
| **Hybrid + RRF** | **A07** | **ถูก** |

<a name="ปัญหา-051"></a>
## ปัญหา 05.1 — การขยายคำพ้องทำให้ผลแย่ลงกว่าไม่ขยาย

**ขั้นตอน:** Retrieval · **สถานะ: เกิดขึ้นจริงและแก้ไปแล้ว**
**ปัญหานี้ไม่ได้อยู่ในแผนตั้งแต่แรก แต่ถูกค้นพบจากการวัดผล**

### อาการที่พบจริง
หลังเพิ่มการขยายคำพ้อง (การแก้ปัญหา 03) คาดว่าคะแนนจะดีขึ้น
แต่ผลการวัดกลับ **แย่ลง**

| ชุดค่า | Hit@1 |
|--------|-------|
| Hybrid (ไม่ขยายคำพ้อง) | 57.8% |
| Hybrid + ขยายคำพ้อง | **52.2%** ← แย่ลง |

### สาเหตุ
โค้ดเดิมนำ **คำถามเดิมและคำพ้องที่เติมเข้าไป มารวมเป็นถุง token เดียวกัน** แล้วค้นครั้งเดียว
ผลคืออันดับของรายการนั้นถูกคำถามเดิมครอบงำ คำพ้องแทบไม่มีน้ำหนัก
และในกรณีที่คำถามเดิมไม่มีคำใดอยู่ในคลังเลย เช่น `"ดัชนีกำลังสัมพัทธ์"`
อันดับที่ได้จากคำถามเดิมเป็นเพียง **สัญญาณรบกวน** แต่ยังได้น้ำหนักเต็ม
จึงกลบเอกสาร RSI ที่ถูกต้องจนมิด

### วิธีตรวจสอบ
1. พิมพ์ค่า signal ของผลลัพธ์ 3 อันดับแรก (`coverage`, `title`, `tag`, `exactTerm`)
2. พบว่าเอกสารเป้าหมาย I02 ไม่ติดแม้แต่ 3 อันดับแรก และทุกเอกสารมี `coverage` ใกล้เคียงกันหมด (~0.14)
   ซึ่งเป็นลายเซ็นของ "การจัดอันดับด้วยสัญญาณรบกวน"

### แนวทางการแก้ไข
แยกเป็น **3 รายการค้นหาที่มาจากคนละแหล่ง และให้น้ำหนักตามความน่าเชื่อถือ**

| รายการ | ที่มา | น้ำหนัก | เหตุผล |
|--------|------|---------|--------|
| คำถามเดิม | ผู้ใช้พิมพ์เอง | 1.00 | น่าเชื่อถือที่สุด |
| คำพ้อง **ล้วน ๆ** | พจนานุกรมที่คัดมาเอง | 0.90 | คัดมาด้วยมือ จึงเชื่อถือได้เกือบเท่าคำถามเดิม |
| Multi-Query | ระบบสร้างเองด้วยกฎ | 0.45 | เป็นการเดา จึงให้น้ำหนักต่ำ |

จุดสำคัญคือรายการ "คำพ้อง" ต้องมาจาก **คำพ้องเท่านั้น ไม่ผสมคำถามเดิม**
มิฉะนั้นอันดับของรายการนั้นจะถูกคำถามเดิมครอบงำอีก ซึ่งเป็นบั๊กเดิม

นอกจากนี้ยังพบว่า Re-ranking ให้คะแนนด้วย **คำถามดิบเท่านั้น**
คำพ้องจึงช่วยแค่ตอนค้น ไม่ช่วยตอนจัดอันดับ จึงแก้ให้ใช้คำถามที่ขยายแล้วในการวัดความครอบคลุมและศัพท์เฉพาะ

### ตำแหน่งใน Source Code
```
rag-retrieve.js  →  retrieve()  แยก baseTokens / synTokens / varTokens + น้ำหนัก W_BASE, W_SYN, W_VAR
                    rrfFuse()   รองรับน้ำหนักต่อรายการ
rag-rerank.js    →  rerank()    ใช้ qBase สำหรับ title match และ qExp สำหรับ coverage/exactTerm
rag-query.js     →  transform() คืนค่า base และ synonyms แยกกัน
```

### ผลหลังแก้

| ชุดค่า | Hit@1 | Hit@3 | MRR |
|--------|-------|-------|-----|
| Hybrid (ไม่ขยายคำพ้อง) | 57.8% | 70.0% | 0.653 |
| Hybrid + ขยายคำพ้อง (ก่อนแก้) | 52.2% | 71.1% | 0.633 |
| **Hybrid + ขยายคำพ้อง (หลังแก้)** | **61.1%** | **76.7%** | **0.710** |

### การทดลองแยกเฉพาะชั้นค้นหา
เดโมในหน้าเว็บสร้างชั้นค้นหาแบบเดิมขึ้นมาใหม่ แล้วเทียบอันดับ **ก่อนเข้า Re-ranking**
(ต้องเทียบก่อน rerank เพราะ rerank เก่งพอจะกู้อันดับคืนได้บางกรณีจนกลบปัญหาที่แท้จริงไป)

คำถาม `"ดัชนีกำลังสัมพัทธ์"` เอกสารที่ถูกคือ I02

| วิธี | อันดับของ I02 ในชั้นค้นหา | ผลที่ตามมา |
|------|--------------------------|-----------|
| วิธีเดิม (รวมถุงเดียว) | **หลุดออกนอกกลุ่มผู้สมัคร 12 ชิ้น** | Re-ranking ไม่มีทางกู้คืนได้เลย |
| **วิธีที่แก้แล้ว** | **อันดับ 5** | Re-ranking ดันขึ้นมาเป็นอันดับ 1 |

จุดที่ต้องเข้าใจคือ ถ้าเอกสารหลุดจากกลุ่มผู้สมัครตั้งแต่ชั้นค้นหา
ไม่ว่าชั้นจัดอันดับจะฉลาดแค่ไหนก็ช่วยอะไรไม่ได้ เพราะมันเห็นเฉพาะสิ่งที่ถูกส่งมาให้เท่านั้น

**บทเรียน:** เทคนิคที่ถูกต้องในทางทฤษฎีอาจทำให้ระบบแย่ลงได้ถ้าประกอบผิดวิธี
ถ้าไม่มีชุดทดสอบเชิงตัวเลข ปัญหานี้จะถูกส่งขึ้นระบบจริงโดยไม่มีใครรู้

## ปัญหา 06 — เอกสารที่ถูกต้องถูกจัดอันดับไว้ต่ำเกินไป

**ขั้นตอน:** Ranking

### อาการ
ระบบค้นเจอเอกสารที่ตอบได้จริง แต่อยู่อันดับ 4–9
เมื่อส่งเข้าขั้นตอนสร้างคำตอบซึ่งใช้แค่ 3 อันดับแรก เอกสารที่ถูกจึงไม่ถูกใช้เลย

### สาเหตุ
การค้นชั้นแรกออกแบบมาให้ **เร็ว** เพราะต้องให้คะแนนทุกเอกสารในคลัง
จึงใช้เพียงความถี่คำเป็นหลัก เอกสารที่มีชิ้นส่วนคำทั่วไปซ้ำเยอะ
จึงได้คะแนนสูงกว่าเอกสารที่ตรงประเด็นแต่สั้นกว่า

### วิธีตรวจสอบ
บันทึกอันดับ **ก่อนและหลัง** rerank แล้วดูว่าเอกสารเป้าหมายเลื่อนขึ้นกี่อันดับ
ถ้าเอกสารที่ถูกมักอยู่นอก 3 อันดับแรกก่อน rerank แปลว่าชั้นแรกจัดอันดับหยาบเกินไป

### แนวทางการแก้ไข
เพิ่มชั้นจัดอันดับใหม่ที่ทำงานเฉพาะผู้สมัคร 12 ชิ้น จึงใช้สัญญาณที่แพงกว่าได้

| สัญญาณ | ความหมาย | น้ำหนัก |
|--------|----------|---------|
| `coverage` | สัดส่วนคำในคำถามที่พบในเอกสาร **ถ่วงด้วย IDF** | 0.60–0.75 |
| `title` | ตรงกับคำถามหลัก/คำถามสำรองของเอกสาร | 0.30 |
| `tag` | ตรงกับ tags ของเอกสาร | 0.22 |
| `exactTerm` | เจอศัพท์เฉพาะตรงตัว เช่น `rsi`, `macd`, `61.8` | 0.18 |

### ตำแหน่งใน Source Code
```
rag-rerank.js  →  rerank(), coverage(), titleMatch(), tagMatch(), exactTermMatch()
config.js      →  USE_RERANK, RERANK_TITLE_BOOST, RERANK_TAG_BOOST, RERANK_EXACT_TERM_BOOST
```

### ผลการทดลอง
คำถาม `"ออเดอร์บล็อกคืออะไร"` (เอกสารที่ถูกคือ A04)

| สถานะ | อันดับของ A04 | อันดับ 1 ที่ได้ |
|-------|---------------|----------------|
| ปิด Re-ranking | อันดับ 5 (นอก 3 อันดับที่ใช้ตอบ) | B03 (คำสั่งซื้อขาย) |
| **เปิด Re-ranking** | **อันดับ 1** | **A04 (Order Block)** |

ผลรวมจากชุดทดสอบ 90 คำถาม: Re-ranking เพิ่ม Hit@1 จาก 61.1% เป็น **75.6%** (+14.5 จุด)
ซึ่งเป็นเทคนิคที่ให้ผลมากที่สุดในระบบนี้

## ปัญหา 07 — ตัวกรอง Metadata ที่ตั้งผิดทำให้คำตอบที่ถูกหายไป

**ขั้นตอน:** Filtering

### อาการ
ผู้ใช้เลือกกรองเฉพาะระดับ "พื้นฐาน" แล้วถามเรื่อง Order Block ซึ่งเป็นเนื้อหาขั้นสูง
ระบบตอบว่าไม่พบข้อมูล ทั้งที่มีเอกสารอยู่จริง

### สาเหตุ
ตัวกรองทำงาน **ก่อน** การให้คะแนน เอกสารที่ไม่ผ่านเงื่อนไขจึงถูกตัดทิ้งตั้งแต่ต้น
โดยไม่มีโอกาสถูกพิจารณาเลย ถ้า metadata ของเอกสารติดป้ายผิด
หรือผู้ใช้ตั้งตัวกรองแคบเกินไป คำตอบที่ถูกจะหายไปทั้งหมด

**นี่คือดาบสองคม** — ตัวกรองมีประโยชน์จริง แต่ก็ทำลายคุณภาพได้เงียบ ๆ

### วิธีตรวจสอบ

ถ้าตัดทิ้งจำนวนมากแต่ผลลัพธ์ที่เหลือคะแนนต่ำ แปลว่าตัวกรองกำลังทำร้ายคุณภาพ

### แนวทางการแก้ไข
- ตั้งค่าเริ่มต้นเป็น "ทั้งหมด" ไม่กรองอะไรเลย
- **แสดงจำนวนที่ถูกกรองออกให้ผู้ใช้เห็นเสมอ** ในหน้าตรวจสอบ Pipeline
- เตือนในกล่องตัวกรองเมื่อมีตัวกรองทำงานอยู่ ว่าถ้าไม่พบข้อมูลให้ลองผ่อนตัวกรอง
- ตรวจ metadata ที่ไม่ครบตั้งแต่ขั้น Ingestion (ดูปัญหา 01)

### ตำแหน่งใน Source Code
```

app.js           →  updateFilterNote()        แจ้งผู้ใช้ว่ากำลังกรองอะไร
config.js        →  USE_METADATA_FILTER, FILTER_LEVEL, FILTER_CATEGORY
```

| ไม่จำกัดระดับ | **A04** | **ถูก** |

<a name="ปัญหา-08"></a>
## ปัญหา 08 — Hallucination: ตอบทั้งที่ไม่มีหลักฐานในบริบท

**ขั้นตอน:** Generation · **สถานะ: เกิดขึ้นจริงและแก้ไปแล้ว**

### อาการที่พบจริง
ทดสอบด้วยคำถามนอกขอบเขต `"ตั๋วเครื่องบินไปเชียงใหม่ราคาเท่าไหร่"`
ระบบกลับหยิบเอกสาร T07 (การวิเคราะห์หลายกรอบเวลา) มาตอบเป็นเรื่องเป็นราว
โดยได้คะแนน **0.427** ซึ่งสูงกว่าเกณฑ์ที่ตั้งไว้ตอนแรก (0.16)

### สาเหตุ (2 ชั้น)
1. **ขั้นตอนสร้างคำตอบถูกออกแบบให้ "ตอบเสมอ"** โดยหยิบผลอันดับหนึ่งมาใช้ไม่ว่าคะแนนจะต่ำแค่ไหน
2. **สาเหตุที่ลึกกว่าและเป็นต้นตอจริง:** ค่า `coverage` เดิมนับ token ทุกตัวเท่ากัน
   แต่การตัดคำภาษาไทยด้วย n-gram สร้างชิ้นส่วนทั่วไปจำนวนมาก เช่น "ที่" "การ" "ราคา"
   ซึ่งปรากฏในแทบทุกเอกสาร คำถามที่ไม่เกี่ยวข้องเลยจึงยังได้คะแนนราว 0.4
   ทำให้ **ด่านกัน Hallucination ถูกหลอกได้**

### วิธีตรวจสอบ
1. เตรียมคำถามนอกขอบเขต 10 ข้อ และคำถามในขอบเขต 90 ข้อ
2. วัดคะแนนหลักฐานสูงสุดของทุกคำถาม แล้วดูว่าสองกลุ่ม **แยกออกจากกันหรือไม่**
3. ถ้าช่วงคะแนนของสองกลุ่มทับกัน แปลว่าไม่มีเกณฑ์ใดที่ตั้งแล้วปลอดภัย

### แนวทางการแก้ไข
**1) ถ่วงน้ำหนัก coverage ด้วย IDF**
คำที่ปรากฏแทบทุกเอกสารได้ค่า IDF เกือบศูนย์ จึงแทบไม่มีน้ำหนัก
ส่วน token ที่ **ไม่เคยปรากฏในคลังเลย** ให้ค่า IDF สูงสุด (เทียบเท่า df = 0)
คุณสมบัติข้อหลังสำคัญมาก เพราะทำให้คำถามนอกขอบเขตซึ่งเต็มไปด้วยคำที่ไม่มีในคลัง
ได้คะแนนต่ำโดยอัตโนมัติ

**2) แยก "คะแนนหลักฐาน" ออกจาก "คะแนนจัดอันดับ"**
สองค่านี้ตอบคนละคำถาม จึงต้องไม่ใช้ค่าเดียวกัน

| ค่า | ตอบคำถามว่า | ใช้ทำอะไร |
|-----|-------------|-----------|
| `score` | ชิ้นไหนดีที่สุด**ในกลุ่มที่ค้นมาได้** | เรียงลำดับผลลัพธ์ |
| `grounding` | หลักฐาน**ดีพอจะตอบหรือยัง** | ตัดสินว่าจะตอบหรือปฏิเสธ |

`grounding = min(1, coverage + 0.35 × title + 0.22 × exactTerm)`

ค่านี้คำนวณ **เสมอ** ไม่ว่าจะเปิดหรือปิด Re-ranking ด่านกัน Hallucination จึงไม่หายไปเมื่อผู้ใช้ปิด rerank

**3) ปฏิเสธอย่างมีข้อมูล** — แจ้งคะแนนจริง เกณฑ์ที่ใช้ และหัวข้อใกล้เคียงที่มีอยู่จริง
**4) บังคับแนบรหัสเอกสารอ้างอิงทุกคำตอบ** ให้ผู้ใช้ตรวจสอบย้อนกลับได้
**5) วัดค่า Faithfulness** ว่าคำตอบตรวจสอบกลับไปยังบริบทได้กี่เปอร์เซ็นต์

### ตำแหน่งใน Source Code
```
rag-index.js     →  idfOf()        ให้ค่า IDF สูงสุดกับ token ที่ไม่มีในคลัง
rag-rerank.js    →  coverage()     ถ่วงน้ำหนักด้วย IDF
                    rerank()       คำนวณ grounding แยกจาก score
rag-generate.js  →  generate()     ด่าน Grounding Check
                    faithfulness() วัดความสอดคล้องกับบริบท
config.js        →  GROUNDING_THRESHOLD, REQUIRE_CITATION
```

### การเลือกค่าเกณฑ์ — วัดจริง ไม่ได้ตั้งลอย ๆ
คะแนนหลักฐานของคำถามนอกขอบเขต 10 ข้อ:
`0.11, 0.15, 0.20, 0.22, 0.23, 0.24, 0.25, 0.29, 0.30, 0.47`

| เกณฑ์ | นอกขอบเขตที่หลุดผ่าน | ในขอบเขตที่ถูกปฏิเสธผิด |
|-------|---------------------|------------------------|
| 0.25 | 3 / 10 | 1.1% |
| **0.30** | **1 / 10** | **3.3%** |
| 0.35 | 1 / 10 | 6.7% |
| 0.40 | 1 / 10 | 10.0% |

เลือก **0.30** เพราะเป็นจุดที่ดักคำถามนอกขอบเขตได้ 9 ใน 10
การขยับขึ้นไปอีกไม่ได้ดักเพิ่มเลย แต่ทำให้ปฏิเสธคำถามที่ถูกต้องมากขึ้นเรื่อย ๆ

### ผลหลังแก้
| สถานะ | คำตอบที่ได้ |
|-------|------------|
| ปิดเกณฑ์หลักฐาน | ตอบเรื่องการวิเคราะห์หลายกรอบเวลา (Hallucination) |
| **เปิดเกณฑ์หลักฐาน** | **"ไม่พบข้อมูลที่สนับสนุนคำตอบมากพอในฐานความรู้ (คะแนนหลักฐานสูงสุด 0.196 ต่ำกว่าเกณฑ์ 0.3)" พร้อมเสนอหัวข้อที่มีจริง** |

### ข้อจำกัดที่ยังเหลืออยู่ (ระบุไว้อย่างตรงไปตรงมา)
คำถาม `"สอนเขียนโปรแกรม python เบื้องต้น"` ได้คะแนน **0.47** จึงยังหลุดผ่านด่านไปได้
สาเหตุคือเอกสาร S04 (Algorithmic Trading) มีคำว่า "โปรแกรม" และ "เบื้องต้น" อยู่จริง
จึงเป็นความเกี่ยวข้องบางส่วนที่แยกด้วยวิธีเชิงคำศัพท์ไม่ได้

**ทางแก้ที่ถูกต้องสำหรับระบบจริง** คือใช้ Embedding Model เชิงความหมายจริง
(เช่น multilingual-e5 หรือ text-embedding-3) ซึ่งเข้าใจได้ว่าคำถามเรื่องการเขียนโปรแกรม
กับเอกสารเรื่องระบบเทรดอัตโนมัติเป็นคนละหัวข้อ ระบบนี้ทำงานบนเบราว์เซอร์ล้วนจึงยังทำไม่ได้

<a name="ปัญหา-09"></a>
## ปัญหา 09 — ชุดทดสอบรั่ว ทำให้คะแนนสวยเกินจริง (Test Set Leakage)

**ขั้นตอน:** Evaluation · **สถานะ: เกิดขึ้นจริงและแก้ไปแล้ว**

### อาการที่พบจริง
รันประเมินผลครั้งแรกได้ผลดีเกินจะเป็นจริง

| ชุดค่า | Hit@1 |
|--------|-------|
| BM25 อย่างเดียว (ไม่มีเทคนิคใดเลย) | **98.2%** |
| ระบบเต็มรูปแบบ | 95.5% |

การที่ระบบพื้นฐานที่สุดได้ 98.2% และการเพิ่มเทคนิคกลับทำให้ **แย่ลง**
คือสัญญาณชัดเจนว่าการวัดผลมีอะไรผิด ไม่ใช่ว่าระบบดีเลิศ

### สาเหตุ
ระบบนำ **คำถามสำรอง (`alt`) ของทุกเอกสารไปใส่ไว้ในหัวของทุก chunk** เพื่อช่วยการค้นหา
แล้ว **ใช้คำถามสำรองชุดเดียวกันนั้นเป็นคำถามทดสอบ**
การวัดผลจึงกลายเป็นการค้นหาข้อความที่ตรงกันทุกตัวอักษร ซึ่งง่ายจนไร้ความหมาย

ที่ร้ายกว่านั้นคือ ขั้นตอน Re-ranking ก็ใช้ฟิลด์ `alt` ในการให้คะแนน `titleMatch`
จึงเกิดการรั่วซ้ำอีกชั้นหนึ่ง

### วิธีตรวจสอบ
ตัวชี้วัดเตือนภัยที่ใช้ได้เสมอ
1. ระบบพื้นฐานได้คะแนนสูงผิดปกติ (> 95%)
2. การเพิ่มเทคนิคที่ควรช่วย กลับทำให้คะแนนลดลง
3. ตรวจว่าข้อความของคำถามทดสอบปรากฏอยู่ในดัชนีหรือไม่

### แนวทางการแก้ไข
แบ่งคำถามสำรองของแต่ละเอกสารเป็น 2 ชุดที่ **ไม่มีทางทับกัน**

```
splitAlt(alt) →  ลำดับคู่  (0, 2, 4, ...) = ชุดที่เข้าดัชนี
                 ลำดับคี่  (1, 3, 5, ...) = ชุดที่กันไว้ทดสอบ
```

ทั้งการตัด chunk การ Re-ranking และการสร้าง Golden Set **ต้องเรียกฟังก์ชันเดียวกันนี้**
เพื่อไม่ให้มีทางเกิดการรั่วซ้ำอีก

### ตำแหน่งใน Source Code
```
rag-normalize.js  →  splitAlt()        แหล่งความจริงเดียวของการแบ่งชุด
rag-chunk.js      →  buildChunks()     ใช้เฉพาะ indexed (ทั้งใน header และฟิลด์ alt)
rag-eval.js       →  buildGoldenSet()  ใช้เฉพาะ heldOut
```

### ผลหลังแก้ — ตัวเลขที่เชื่อถือได้ (Golden Set 90 คำถามที่ไม่เคยเข้าดัชนี)

|---|--------|-------|-------|-------|-----|--------|

**สรุปการมีส่วนช่วยของแต่ละเทคนิค (วัดด้วย Hit@3)**

"BM25 เปล่า ๆ ก็ได้ 98% แล้ว เทคนิคอื่นไม่จำเป็น" ซึ่งผิดทั้งหมด
**คุณภาพของการวัดผลสำคัญไม่น้อยกว่าคุณภาพของระบบ**

## ปัญหา 10 — คำแนะนำการลงทุนรายบุคคล และข้อมูลล้าสมัย

**ขั้นตอน:** Safety & Operations

### อาการ
ผู้ใช้ถามว่า `"ตอนนี้ควรซื้อตัวไหนดี"` หรือ `"ราคาพรุ่งนี้จะขึ้นไหม"`
ถ้าระบบตอบ จะกลายเป็นการให้คำแนะนำการลงทุน ซึ่งเกินขอบเขตของฐานความรู้เพื่อการศึกษา
และอาจสร้างความเสียหายทางการเงินให้ผู้ใช้จริง

### สาเหตุ
RAG ถูกออกแบบมาให้ "ค้นแล้วตอบ" โดยไม่มีชั้นพิจารณาว่า **คำถามนี้ควรตอบหรือไม่**

จุดที่ต่างจากปัญหา 08 อย่างชัดเจน
- ปัญหา 08 = **ไม่มีหลักฐาน** จึงไม่ควรตอบ
- ปัญหา 10 = **มีหลักฐาน** แต่ไม่ควรนำไปตอบในรูปแบบคำแนะนำรายบุคคล

ยิ่งระบบค้นเจอข้อมูลมาก คำตอบยิ่งดูน่าเชื่อถือ และยิ่งอันตราย

นอกจากนี้ ข้อมูลบางหมวด เช่น ภาษีและกฎระเบียบ เปลี่ยนแปลงตามประกาศ
จึงล้าสมัยได้แม้เนื้อหาจะถูกต้องในวันที่เขียน

### วิธีตรวจสอบ
1. ตรวจคำถามด้วยรายการรูปแบบที่บ่งชี้การขอคำแนะนำรายบุคคล **ก่อนเข้าขั้นตอนค้นหา**
2. ตรวจฟิลด์ `updated` ของทุกเอกสารที่ถูกใช้ตอบ ว่าเกินเกณฑ์อายุที่ยอมรับได้หรือไม่

### แนวทางการแก้ไข
- **Safety Guard เป็นชั้นแรกสุด** ของการสร้างคำตอบ ดักด้วยรูปแบบ 17 แบบ
  เช่น "ควรซื้อตัวไหน", "จะขึ้นไหม", "ทำนายราคา", "การันตีกำไร", "กู้เงินมาเทรด"
- **ไม่ปฏิเสธเปล่า ๆ** แต่เสนอคำถามเชิงหลักการที่ระบบตอบได้จริง 3 ข้อแทน
- **เตือนความสดของข้อมูล** เมื่อเอกสารที่ใช้ตอบเก่ากว่าเกณฑ์ (ค่าเริ่มต้น 18 เดือน)
- เนื้อหาหมวดภาษีเขียนแบบระบุหลักการกว้าง ๆ และบอกให้ตรวจสอบประกาศล่าสุดเสมอ
- แสดงคำเตือนถาวรในหน้าเว็บว่าเป็นเนื้อหาเพื่อการศึกษา ไม่ใช่คำแนะนำการลงทุน

```
                    freshnessWarning()   ตรวจอายุเอกสาร
config.js        →  SAFETY_PATTERNS (17 รูปแบบ), SAFETY_GUARD
                    FRESHNESS_WARNING, FRESHNESS_MONTHS
index.html       →  คำเตือนถาวรในกล่องต้อนรับและส่วนท้ายเว็บ
```
