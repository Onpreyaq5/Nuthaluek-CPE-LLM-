=============================================================================

INTERNAL ARCHITECTURE
  api/router.py
       -> Pydantic contract (schemas/contracts.py)
       -> service layer
       -> SQLAlchemy model/database

  services:
    events.py             batch ingest + idempotency + gateway compatibility
    feedback.py           analytical feedback + review queue
    recommendations.py    compose structured results from 06/07
    alerts.py             A1-A5 + web notification deduplication
    analytics.py          aggregate metrics; never expose row-level PII
    calendar_export.py    RFC 5545 .ics generation
    privacy.py            recursive PII scrubbing
    data_privacy.py       delete by student_hash

  workers:
    celery_app.py         Redis-backed Celery configuration
    tasks.py              event-log retention cleanup

RESPONSE CONTRACT
  success:
    {"ok":true,"data":{},"meta":{"request_id":"..."}}

  error:
    {"ok":false,"error":{"code":"...","message":"...","details":...},
     "meta":{"request_id":"..."}}

  /health, /ready และ /metrics เป็น infrastructure endpoints จึงไม่บังคับ envelope

EVENT FLOW
  service 01-07
    -> Module 02 in-memory queue (ไม่บล็อก user response)
    -> POST /events/batch
    -> validate + reject raw ID + scrub payload
    -> deduplicate เฉพาะเมื่อมี event_id
    -> event_logs + Prometheus

  Event names ที่ 02 ส่งจริง: plan_validate, plan_auto, chat_message, feedback
  08 ไม่บังคับ 02 เปลี่ยน field/event; รับ event -> action และ id_hash -> student_hash
  request_id ใน body ไม่มีได้ เพราะ 02 ส่ง X-Request-ID header

  ถ้า action=feedback และ payload มี target_type/target_id/rating:
    -> feedback_events
    -> rating 1-2 เข้า review_queue

  02 ยังไม่ส่ง event_id; หาก retry อาจนับซ้ำ และ 08 จะไม่เดา ID จาก payload

FEEDBACK CONTRACT
  คะแนนมาตรฐาน = 1..5 (เลือกตาม contract ปัจจุบันของ Module 02)
  target_type = plan | chat_message | explanation
  source_feedback_id = ID จาก source system ใช้ idempotency
  02 ปัจจุบันส่ง feedback ผ่าน event queue โดยไม่มี feedback_id/reason
  ดังนั้น review queue มี rating แต่ไม่มีเหตุผล และ retry อาจสร้างสำเนา

  Ownership:
  - Module 02 ตรวจ JWT, ตรวจว่า target เป็นของผู้ใช้ และเก็บข้อมูล transactional
  - Module 08 รับเฉพาะ student_hash และเก็บ analytical copy/review workflow
  - Module 08 ไม่รับ student_id และไม่มีหน้าที่ authenticate นักศึกษาโดยตรง

RECOMMENDATION RULE
  Module 06 เป็นผู้ตัดสิน conflict/credit/prerequisite/seat เท่านั้น
  Module 07 เป็นผู้สร้างข้อความอธิบายและ citation
  Module 08 มีหน้าที่ประกอบผล ไม่เปลี่ยนตัวเลข ไม่สร้าง conflict ใหม่
  ทุก response ต้องมี disclaimer:
  "ระบบนี้เป็นเครื่องมือช่วยวางแผนเบื้องต้น ไม่ใช่การยืนยันจากมหาวิทยาลัย
   โปรดตรวจสอบกับระบบทะเบียนและอาจารย์ที่ปรึกษาก่อนลงทะเบียนจริง"

ALERT PROCESS
  ตัวเรียกภายในส่ง snapshot ของ academic events, planned sections และ credits
    -> evaluate A1-A5
    -> dedup key = student_hash:code:reference:as_of
    -> บันทึก notification channel=web, status=sent

  email/LINE ต้องมี 3 อย่างก่อนเปิดใช้:
  1. recipient mapping ที่อยู่นอก analytics DB
  2. consent/opt-out ของผู้ใช้
  3. secret/config จากเฟิส

ANALYTICS DEFINITION
  Plan Positive Feedback Rate = plan feedback rating >= 4 / plan feedback ทั้งหมด
  Plan Acceptance Rate = null จนมี event ยืนยันการใช้/บันทึกแผนจริง
  Negative Feedback    = rating <= 2
  P95 latency          = percentile จาก event.latency_ms ในช่วงที่เลือก
  Unanswered Question  = null จน 02 ส่ง chat outcome ที่วัดได้
  Invalid Validation   = plan_validate ที่ payload.is_valid = false
  Frequent Conflict    = conflict code เฉพาะเมื่อ event ส่งรายละเอียดมา

PRIVACY / PDPA
  - student_hash เท่านั้น; raw student ID ถูก reject
  - ตัด sensitive keys และ mask ID/โทรศัพท์/email ใน nested payload
  - endpoint analytics/alert/notification/delete/POST ICS ต้องมี INTERNAL_API_TOKEN
  - หาก token ไม่ถูกตั้ง endpoint ภายในจะตอบ 503 (fail closed)
  - /events และ /feedback ยังไม่บังคับ token เพื่อคง compatibility กับ 02;
    ต้องจำกัด private network และตกลง service authentication ก่อน production
  - retention default 90 วัน ปรับได้ด้วย LOG_RETENTION_DAYS
  - DELETE /privacy/students/{student_hash} ลบข้อมูล analytics ของ Module 08
  - transcript/เกรดไม่ควรผ่าน service นี้

DATABASE OWNERSHIP
  Module 08 สร้าง/ใช้:
    event_logs
    feedback_events
    review_queue
    notifications

  ไม่อ่าน plans/plan_items/feedback table ที่ Module 02 เป็นเจ้าของ
  ICS รับ ownership-checked snapshot ผ่าน POST /export/ics เท่านั้น
  GET /export/ics/{plan_id} ตอบ 503 จนกว่าจะมีการเชื่อม owner check จริง

  Production ต้องย้ายจาก create_all ไป migration กลางเมื่อทีมตกลง schema แล้ว
  การแก้ infra/db เป็นหน้าที่เฟิส จึงไม่ได้แก้จากงาน Module 08

FAILURE POLICY
  - event/feedback duplicate: ตอบสำเร็จพร้อม duplicate=true/count
  - database ไม่พร้อม: /ready ตอบ 503
  - GET ICS เดิม: PLAN_EXPORT_NOT_CONNECTED 503 เพื่อไม่ข้าม owner check
  - payload ไม่ถูกต้องหรือมี raw ID: VALIDATION_422
  - Module 02 ต้องส่ง log แบบ async; 08 ล่มต้องไม่ทำให้ user request หลักล้ม

CONTINUOUS IMPROVEMENT LOOP
  ใช้งาน -> log -> analytics -> review queue -> แยกสาเหตุ
  -> ปรับ prompt/document/rule/scoring -> deploy -> วัดซ้ำ

METRIC เป้าหมายระดับระบบ

  - Answer Accuracy golden set >= 85% (วัดที่ Module 07)
  - validate P95 < 500ms
  - auto-plan P95 < 10s
  - chat first token < 2s
  - cost / active user / month
